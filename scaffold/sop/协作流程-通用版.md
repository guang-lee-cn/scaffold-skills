# 协作流程（Scaffold 通用版 v1.0）

> 项目参数一律引用 `pj-config.md`；本文件只含跨项目公共流程。
> 权威关系：项目的 `docs/开发交付/工程流程.md` 是该项目的唯一施工口径，由两部分组成——指向本文件与 `policies/` 的**索引**（正文不复制，单一源在脚手架），加上本项目特有的增删。两者冲突时，项目特有的增删优先，索引到的正文按脚手架生效；差异记进项目的偏离记录。

## 1. 执行形态

架构师常驻单 session + dev / QA subagent 瞬态拉起（可并行）。

**执行期 G 零介入**：凡是原本需要「报 G / 等 G 拍板」的事，执行期一律改成「架构师裁决 + 写入开发状态.md」，留待项目结束复审时一起看。项目流一旦启动，不因等确认而中断。

**并行 agent 各占一棵工作树时**，技能必须装进每棵树（`install-skills.sh --worktrees`）或装到 user 级；只在主检出装过，等于执行现场没有技能，清单对它们失效。

**并行度由共享可变资源决定，不由工作量决定**：

- 架构师恒为 1（唯一决策者 + 唯一写状态文件），两个架构师直接违反分权；
- QA 与作者必须是不同实例，否则那条"独立评审"是自证；
- 并行 dev 数以「文件范围不相交 + 门禁串行」为上限。门禁 run 的证据口径是 `dirty == 0` 且 `commit == HEAD`，**只要有 agent 在跑门禁期间写仓库（哪怕只是写报告），那次 run 就作废**——赶工突破这个上限，换来的是一批只能当调试记录的数字。

**一张卡一个写者**：卡的粒度由「能否独立验证」定，不由「能否并行」定。同一张卡拆给两个人，等于让第二个人改第一个人还没编译过的代码，而且两人会撞同一棵树。

这三条项目侧的具体值（门禁是否独占、participant 域号分配、单次门禁耗时）写进 `pj-config.md`，不由执行模型现场猜。

## 2. 主线

方案 → 台账行 → 独立评审 → 架构师裁决 → 派卡 → 小步实现 → commit → QA / 架构师验收 → 集成 → 按卡 push

返工在卡内闭环，不回头找 G。评审驳回不改变主线，只改变这一轮的产出。

## 3. 角色边界

只写唯一职责，其余靠 §2 的主线隐含：

- **架构师**：唯一决策者，唯一写 `开发状态.md` 与问题台账的人。派发只给「目标 + 设计输入 + DoD + 硬约束」，不给实现步骤；自己改代码即失去裁决资格。
- **Dev**：实现 + 门禁全绿 + 交接。可质疑架构师，限 2 轮；第 3 轮执行，不再讨论。
- **QA**：独立评审，只报有证据的缺陷。不参与实现，不裁决。
- **G**：项目结束后与架构师做一轮复审（这轮不是全自动）。执行期不介入。

## 4. 两层门禁

| 门 | 时机 | 判据 |
|---|---|---|
| 方案评审 | 方案成文后、派卡前 | 见 `policies/方案评审门禁.md`——两份独立评审是否指出了「按此写下去会出事」的具体位置 |
| 代码评审 | 每卡实现完成、push 前 | 见 `skills/ai-code-review/`——finding 是否带证据定位与定级 |

两层都不看「写了多少」，只看「有没有定位到具体位置」。

**证据级**（门禁结果能不能拿来论证）只有一个口径：`quality/runs/<日期>/<run-id>/summary.json` 里 `git.dirty == 0` 且 commit 非空。脏树上的 run 只能当调试记录；拿脏 run 说「回归了」按假绿处理。

## 5. 缺陷与偏离

- 每个缺陷一条台账行，终止态只有两个：`closed`（改了且验证过）、`wontfix`（写理由）。没有第三种。
- 与规范不一致的做法记一条偏离（DV），写明规范要求、本项目做法、原因、影响、复核时机。
- 模板：`templates/问题台账.md.tpl`、`templates/偏离记录.md.tpl`。

## 6. 提交与 push

见 `policies/git规范.md`。要点：一个 commit 一个可回滚修改；一张卡一次 push；历史只增不改。

**push 是唯一的对外放行点，因此它不是机械动作**：

- 缺 QA 评审记录的卡**不得 push**；架构师自评审不能替代 QA 评审（自评审有盲区，实测漏得掉并发与生命周期类缺陷）
- 已经误推的，按 §5 立台账，并在**下一次 push 前**补一次独立评审——评审对象是**已推的那个 commit**，不是「下一版」
- 缺陷已经合并且已推，就不回改历史，开一张**追补卡**：只含注释与用例，用**变异**证明新用例对缺陷敏感（删掉修复点 ⇒ 用例必红），附变异 diff / 红 / 还原后绿三段证据

## 7. 调研先行

涉及外部组件能力边界、并发 / 生命周期 / 资源释放的设计，先调研再定方案，产出三张表（数据源 / 证据 / 数字）。见 `policies/调研先行.md`。

## 8. 特殊流程强制复盘

故障 / 方案矫正 → 三层根因（技术 - 流程 - 组织，组织根因与技术根因分开管）+ 模式沉淀入 skills + 外部案例库补一行。

**每批关闭前**（不是只有故障才做）：`进度.md` 的已关卡拉证据 → 写当批复盘报告（含「批次指标」与「规则命中表」），路径填进批次行的 `复盘` 列 → 跑 `quality/check-flywheel.sh --project .`，退出码非 0 不得关批。这三步是脚手架自我改进的唯一通道：指标看趋势（逃逸率、假绿、变异覆盖），命中表删无效规则，零命中连续两批即退役。

**谁在推动**：架构师推动，但**不靠记性**——`run_gate.sh` 开跑前读 `进度.md` 的批次表，只要还有批次不是 `已关闭` 就拒绝开跑（exit 3）。全自动流程里没有外部提醒者，唯一的强制点是「下一批的第一步被上一批没做完的事挡住」。批次行只有三个状态：`进行中` → `待复盘` → `已关闭`，跳级等于把闸门绕开。

## 9. 报告双文档

主报告人可读，禁黑话；门禁 JSON / 证据链 / 精确栈另行存档（`quality/` + 日期目录）。数字进报告前先入数字登记表，口径写成完整一句话。

## 9.1 多 agent 通信（卡 + 线程，而不是共享状态文档）

文件系统是唯一在所有执行形态下都成立的通道：并行 worktree 的 agent 不共享进程、不共享聊天上下文，只共享文件。

- **一张卡一个目录**：`<日期>/<卡号>/{卡.md, thread.md, 交接.md, 评审.md}`。`卡.md` 是派发，`thread.md` 追加写提问、答复、裁决、重开。
- **只读自己的线程**：不需要为了拿一条指令去读整个项目的状态文档——那是广播，读一次吞下全部历史。
- **状态文档只写决策**：`开发状态.md` 不再承载逐卡问答，只写「为什么这么定」+ 指向 thread。同一句话不写两遍。
- **聊天可先到，落盘才算数**：对话会被压缩、会被新任务挤出；没进 thread 的结论下一轮引用不到。
- **提问与回执都要结构化**：提问带「卡在哪 + 试过什么 + 要我定哪个选择」；交接带「改了什么 / 证据 / 偏差 / 风险 / 待定」；评审带「P 级计数 + 定位」。散文式汇报等于把分析成本转给对方。

## 11. 项目结束复审清单（G + 架构师）

这轮不是全自动，是本流程唯一的强制人工关口。逐项看：

1. 偏离记录逐条裁决：改规范，还是保留本项目做法并写明适用条件
2. 台账是否全部落到终止态；`wontfix` 的理由是否站得住
3. 每个 P0 缺陷是否做过反例检验（「有没有可能不是这个根因」）
4. **零引用资产**：`scaffold/policies|templates|sop` 里没有任何文件指向的条目，两个项目都没用就删（用 `skill-lint.py` 的零引用警告当数据源，别靠记性）
5. **回流候选逐条裁决**（`docs/开发交付/回流候选.md`）：采纳的在本仓改并写回 commit，不采纳的写理由；连续两个项目都不采纳的候选，从模板里删
6. 外部案例库新增条目是否值得回流 scaffold
7. 回灌落点：改 scaffold 的，改在本仓；只属本项目的，留在项目 `skills/` 或 `docs/`；裁决记录写进 `scaffold/review/<日期>-<项目>-<主题>.md`（回流入口留档，下次评审从这里看得到上次结论）

## 12. 归档

旧 SOP 版本归档保留；流程切换以复审结论为准，执行期不改流程。
