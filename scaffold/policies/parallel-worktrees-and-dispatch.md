# 并行工作树与派发（多 agent 机械规则）

> 适用：同一项目里 ≥2 个会写文件的 agent 同时干活。
> 不适用：只读调研、单 agent、门禁串行窗口。
> 上游条款见 `sop/collaboration-flow.md`「并行度由共享可变资源决定」——本文只补**机械动作**，不重复判据来源。

## 一、一棵树一个写者

- 每个会改文件的 agent 各占一棵 `git worktree`，分支名 `lane/<卡名>`；主检出只做集成与基线构建，不承载任何写者。
- 同树双写者的唯一结果是把对方的半成品卷进自己的提交——这不是概率问题，是时间问题。
- **反例（实测）**：三个 agent 共用一棵树时，`git commit` 撞 `index.lock`，而 `git add -A` 会把另一个 agent 正在改的文件一起提交；工作树"看起来干净"只说明还没写到那一步。

## 二、并行上限按文件清单判

- 划卡时列出每张卡的**文件清单**，交集非空即串行；按"模块/子系统"划会漏掉共享头文件（`facade_impl.hpp`、`Context.hpp` 这类）。
- 与"一张卡一个写者"叠加：一张卡不拆给两人，两张卡不共用一个文件。

## 三、技能装载的正确调用

```bash
bash scaffold/install-skills.sh --project <主检出> --worktrees
```

- **对 worktree 路径直接跑 `--project <wt>` 会报「缺清单」**：`skills/skills.conf` 在主线，worktree 里没有（项目侧 `skills/` 常被 `.gitignore` 忽略）。这是设计如此，不是故障。
- `--user` 只作兜底（`~/.claude/skills`），不作默认：user 级会让"这条 lane 该装哪些"失去项目边界。
- 校验口径：输出里的 `worktree 合计: 声明 N / 就绪 N / 缺失 0`；缺失不为 0 等于执行现场没有规范。

## 四、提交纪律

- 只用 `git add <显式路径>`；**禁 `git add -A`、`git commit -a`、`git commit .`**。
- 一卷一分支，合回主线用 `--ff-only` 或 rebase，**不 squash**——哈希要保留，门禁 run 与 QA 记录按哈希指认，改写即断链。

## 五、构建隔离

- 一棵树一个 build 目录，名字带用途（`build-<lane>`）；**禁止用主树的 build 目录编 worktree 的源码**——CMake 绑定源路径，会静默编到错误目录或直接失败。
- 跨 agent 共用全局锁：`flock /tmp/<项目>-build.lock`（构建）、`/tmp/<项目>-net.lock`（跑网络/端口类用例）。锁名写进 `pj-config.md`，不各自发明。
- 并发构建要限并行度（`-j` 之和不超过核数），否则两个全量构建互相拖成三倍时间。

### 5.1 资源护栏（CPU / 内存 / 链路）

只限 `-j` 不够——**内存压力与唤醒延迟才是把 IDE 和 agent 前端拖断的那一环**。

- **同一时刻只允许一个重构建**：全量门禁、sanitizer、valgrind 互斥。两条并行不是「省时间」，
  是两边都变慢，而且取证读数失真（时间变长、分位数不可比）。
- **边界放到 VM / 容器层，不要放在每个脚本里**。脚本各自写启发式总有漏网的（新脚本、手工命令、
  agent 临时跑一次）。示例（WSL）：`.wslconfig` 里 `processors=<核数-2>`、`memory=<实测单卡峰值×并发数×1.2>`、`swap=0`。
- **`swap=0` 的理由必须写下来**：内存溢出时让内核 **OOM 杀掉那条构建命令**，而不是 swap 到慢盘。
  swap 风暴会抢走宿主的磁盘 I/O —— 那才是「整机假死、IDE 与 agent 断链」的真身。
  宁可一条命令失败，不要整机失去响应。
- **探针即判据**：轻探针（`echo` 类）延迟超过**空闲基线的 10 倍**即视为已饱和；无基线时用绝对阈值 5 s。
  取先到者。判定成立就立刻降并行度或等它跑完。
  不要用「再等等看」代替判据——等到的是 agent 与 IDE 双双掉线。
  *为什么用相对基线*：4 核机器重编译时 `echo` 慢到 5 s 是正常的，14 核上 5 s 已属异常；
  同一个绝对数字在两种机器上会被解读成相反结论。
- **`nice` 不是护栏**：构建是长时间 CPU 密集，`nice` 只让它变慢、不减少占用；
  真正有效的是「少放一个重任务进来」。


## 六、门禁是全局互斥资源

- 门禁 run 的证据口径是 `dirty == 0` 且 `commit == HEAD`；只要还有 agent 在写仓库（哪怕只写报告），那次 run 作废。
- 并行档下门禁**不是每 lane 一份**：合完再跑，跑的时候全体停写。

## 七、合并顺序

- 按依赖拓扑合：被依赖的先合（例如生成器改动先于用它的用例）。
- 每合一条跑一遍门禁再发下一波；合完立刻删 worktree（`git worktree remove`），残留的树会被后续 agent 误用。

## 八、判据（反写：怎么算这轮并行没出事）

1. 主检出 `git status --porcelain` 为空；
2. 每条 lane 的 `git show --stat` 只含本卡文件清单里的路径；
3. 每条 lane 的提交里没有别人正在改的路径；
4. 主检出的构建树没有被 lane 改动的源码污染（构建产物时间戳早于 lane 提交即作废）；
5. 构建期间 `load(1m) ≤ nproc`（常态）且 `≤ nproc × 0.5`（取证 / 测量期）；
6. 构建期间可用内存 ≥ 2 GiB（`swap=0` 时尤其），且轻探针延迟 ≤ 空闲基线的 10 倍（无基线时 ≤ 5 s）。

任一不成立，说明第一至六条有某条被绕过了，不算"运气不好"。

## 九、项目侧要落的值

写进 `pj-config.md`：锁文件路径、单次门禁耗时、并发构建的 `-j` 上限、`skills.conf` 是否入库（决定 `--worktrees` 能否直接用）、**资源边界（核数 / 内存 / 交换上限的落点与当前值）与重构建互斥方式**。这几项不落，执行模型只能现场猜。

## 十、进度可见性

- 并行 lane 的进度用**受管后台任务**暴露（每 5–10 s 打一条快照：分支 / HEAD / 脏文件数 / 最近提交 / 编译进程数），不要用 `nohup` 脱离任务系统。
- 判据：脱离任务系统的进程，宿主 UI 里看不见——等于没有状态，用户只能问"还在跑吗"。
- 快照只读 git 与 `/proc`，不写仓库、不参与门禁，因此不受 `dirty == 0` 约束；但**不得**顺手在里面跑构建或测试（那就是另起一条门禁）。
- 给 `wsl bash -c` 传含 `$()`、`$i`、`||`、`|` 的命令时一律写成脚本文件再执行：宿主 shell 会先展开一遍，内联转义不可靠（同一天踩过两次）。
