# 方案评审门禁（发卡前）

> 由来：设计缺陷拖到实现阶段才发现的代价是重写；在方案阶段被两份独立评审抓出来，代价只是一次整改。
> 适用范围：要改结构 / 接口 / 并发 / 生命周期的方案。改文案、改常量不适用。

## 门禁

方案成文后、派卡前，必须有两份**独立**评审，评审者之间不共享中间结论：

- **实现视角**（要动手的人）：这个方案能否实现、缺哪些前置条件、边界在哪、依赖的接口是否真有这个能力
- **验收视角**（QA）：能否被测试验证、失败路径是否覆盖、**观测面两问**（能记录什么 / 能据此回答什么可证伪的判断），口径见下节

架构师对每一条意见裁决，三选一：接受 / 驳回（写理由）/ 转成台账条目（暂不修）。

裁决完成后方案升版，**再发卡**。未过门禁不得发卡。

## 观测面的价值分层（设计输入）

> 由来：把「可观测性够不够」当成一个配额问句，只会产出记录层——日志、缓冲、导出都在，
> 却没有任何环节因数据而改变。本节只规定提问结构与判据，不规定算法、组件、阈值，
> 也不要求每批都做到分析或决策。

方案成文时必须声明三项，缺一项按本节反写判据处理：

| 项 | 要写什么 | 不算数 |
|---|---|---|
| 价值层 | 本批落在 **记录 / 分析 / 决策** 哪一层（可只做记录） | 只写模块名或依赖层次（L0/L1/L2）；依赖分层不等于价值分层 |
| 消费者 | 产出由谁消费；写不出具体角色或环节，就写「本批无消费者」＋接手者与时点 | 「供后续分析使用」 |
| 可证伪判断 | 由数据得出的判断句，含对象与可比较对象（例：能判定本次 p99 抬升是否由分片配置变化引起） | 「支持分析 / 便于定位 / 提升可观测性」 |

**反写判据**：一份设计若只能列出「记录 / 导出 / 查询」，而写不出判断句与消费者，判为**未覆盖分析面**。
处置不是判失败，而是要求写明「本批不做、由谁在何时接」——**允许分阶段，不允许无人接手**。

**「智能」的最小形态**：判断会改变下一步动作（闭环），不是加一个推理模块。
采集 → 汇总成趋势 → 趋势变成门禁判据，即使没有算法也构成分析面。

**现有能力盘点**：方案还要声明「涉及 / 复用 / 绕开本仓哪些已有能力」，引用项目的能力清单；
写「无仓内候选」要给理由。这条与是否可观测无关，用来防止重复造、也防止已有底座被忽略。

不规定：用什么算法、加不加模块、阈值多少、必须做到哪一层。这些是手段，
按 `constraints-and-criteria.md`「只压错误，不压能力」不进规范。

## 判据（反写）

只有一条：**评审有没有指出「按这个方案写下去会出事」的具体位置**——文件:行、状态机节点、时序交错点、某个接口的实际返回值。

只给出「建议加强测试」「注意并发」「考虑扩展性」这类没有定位的意见，视为未评审，重做。

## 常见失效

- 两份评审由同一上下文产出 → 不算独立
- 只评代码不评方案 → 属于代码评审，不是本门禁
- 评审提了意见但没有裁决 → 等于没评
- 评审者被事先告知「结论是什么」→ 会回来确认你的假设，而不是找反例

## 对弈制（Adversarial Pairing）

本门禁的加强形态：不是「两份评审各说一遍」，而是**提案方与反方对弈，第三方裁决**。它服务 `top-principles.md` §1–§3，不替代本门禁的常规两评。

### 触发（可机械判定，满足任一）

判据是**改动路径**，不是评审者的感觉。先取本卡的起点，再跑一条命令看命中的形态：

```bash
# BASE = 本卡分支与默认分支的分叉点（默认分支取 pj-config.md 的「分支/基线」）。
# 不是 HEAD~1：一张卡多个 commit 时只看最后一个，整张卡的契约改动会被漏掉；
# 也不是默认分支的尖端：那会把同批别卡的历史算进来，让每张卡都触发对弈。
BASE="$(git merge-base HEAD "$(sed -n 's/^分支\/基线:[[:space:]]*//p' pj-config.md | head -1)")"
git diff --name-status "$BASE"..HEAD
```

| 检出形态 | 触发项 | 服务的准则 |
|---|---|---|
| 命中 `**/include/**` 或 `**/*.idl` | 改公共契约 | Global Over Local |
| `--diff-filter=ADR -- '**/src/**'` 非空；或某个既有文件的删除行数 > 新增行数 | 替换或引入实现 | Reuse First |
| 命中 `quality/**`、`**/gates*.conf`、`scaffold/**` | 新增或改变门禁 / 判据 | Falsifiability |
| `git diff --name-only "$BASE"..HEAD \| cut -d/ -f1 \| sort -u \| wc -l` ≥ 2 | 跨层改动 | Global Over Local |

不设「文件数 / 行数」阈值：没人量它，拆 commit 就能绕，而拆 commit 本身违反「一个逻辑变更一个 commit」。

### 三方

| 角色 | 谁 | 产出 | 硬约束 |
|---|---|---|---|
| 提案方 | 卡 owner | 主张 + ≥2 备选 + 代价表 + 可证伪判据（Red / Green / Counter）+ 系统影响三件 | 判据在动手之前写 |
| 反方 | 新上下文，只拿到主张、需求与代码 | 反例；主产出是**破**，不另提方案 | 不拿提案方的代价表（防锚定）；prompt 存档 |
| 裁决方 | 未参与提案者 | 采纳 / 不采纳 + 依据 + 落 DV | **提案方不得自裁** |

### 反例模板（四字段，缺一即不可判）

1. 被攻击的断言 + `file:line`
2. 可执行触发器：命令 / 输入 / 时序交错
3. 期望 vs 实际，并落 artifact
4. 判别性：主张为真时应当看到什么

「找不到反例」必须附 run id 与实跑输出。只写「建议加强测试 / 注意并发 / 没发现问题」→ 视为未评审。

### 自我裁决的禁法

架构师是提案方时（换实现、定契约通常如此），不得自己裁决：上报用户，或交给一个只拿到「主张 + 冻结判据」的新上下文。只有一人可用时，标「未裁决」并**卡住 push**——不许同上下文自审。

### 留痕

`<交付文档目录>/对弈/<决策-id>.md`：主张 / 反例 / 裁决三段。DV 的证据列指向它，不重复正文。

## 产物

- 两份评审报告（各自独立，不合并）
- 一份裁决表：意见 / 裁决 / 理由 / 落到哪张卡
- 方案升版时的变更摘要
- 触发对弈时：对弈记录（三段式，见上）

评审报告模板：`templates/design-review-report.tpl`（一份报告只出自一个评审者，两份不合并）。
