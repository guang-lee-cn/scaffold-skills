# Agent 协作的介质与裁剪

> 与 `token-discipline.md` 互补：那份讲「少花」，这份讲「花在哪、用什么装」。
> 适用于任何「人在环上 + 多个 agent 异步协作」的项目，与具体语言/框架无关。

## 一、先判面，再选介质

| 面 | 内容 | 介质 | 理由 |
|---|---|---|---|
| **控制面** | 意图、判据、决策、复盘、被否方案 | **Markdown** | 人机同读、可 diff、可审计、崩溃可续 |
| **状态面** | 批次/卡/门禁状态、谁在做什么 | **结构化小文件**（json / sqlite） | 只需被查，不需被解释；单一写者 |
| **数据面** | 原始日志、样本、二进制、时序 | **文件 + 摘要指针** | 体积大、只需被引用，进上下文就是浪费 |
| **实时协调** | 抢占、锁、心跳 | **不做**；用 worktree 隔离 + 一卡一写者 | 文件无并发语义，伪锁比没锁更危险 |

判据一句话：**要被解释的进 md，要被查的进结构化，要被引用的留文件。**

## 二、共享内存不是 agent 通信的升级

- 对 agent 而言，介质的实际成本 = **进入上下文的 token × 读取次数**；
  搬运成本（拷贝、传输、序列化）相对 tokenize + attention 可忽略。
- 任何介质最终都要渲染成文本才被理解。因此 **shm / 消息队列 / RPC 的收益在进程间字节传输，不在 agent 之间**。
- 把数据面的工具搬到控制面，换来的是运维负担与可审计性丢失，不是速度。
- 同理：**分钟级到小时级的异步链路是批处理，不该用消息总线**。

## 三、状态面必须单一事实源

同一事实只许**一处可写**，其余位置只放指针。

- 反例：批次状态同时写在进度表、状态文档、卡片里——副本必漂，且无人负责更新
  （典型症状：同一个计数在三份文档里是三个数）。
- 正例：一个 `status.json` 似的结构化文件由单一写者维护，文档只写「见 xxx」。

## 四、三条裁剪规则（可机械检查）

1. **首屏摘要块**：卡 / 交接 / 评审的第一节固定四段、≤10 行——
   `做什么` / `不做什么及原因` / `验收判据` / `关联路径`。读者只读首屏即可开工，细节按需下钻。
   *「不做什么及原因」是最常被漏、也最值钱的一段：没有它，下一个人会把被否的方案再走一遍。*
2. **传指针不传全文**：引用写成 `路径#L20-40`。转述会错，指针不会。
3. **原始数据不入文档**：日志与样本留在磁盘旁路，文档只放统计摘要 + 路径。

## 五、判定（怎么知道做到了）

- 新角色开工必读 **≤ 8K 字**（约 5K token）；超了说明常驻链该拆，不是 agent 不够聪明。
- 交接里的路径**能直接打开且行号命中**。
- 同一事实在仓库里**只有一处可写**。

## 六、常见错误

- 常驻链里塞历史叙事（规则：每份 ≤200 行，超了拆专题、链上留指针）
- 用 md 存批次/卡片状态
- 把原始日志或整篇文档粘进交接
- 用消息队列做分钟级批处理
- 把「更快的传输 / 共享内存」当成 agent 协作的优化方向——瓶颈在注意力，不在带宽
