# 调研先行与外部案例库

## 什么时候必须调研

- 要拿外部组件 / 库 / 协议的能力边界当设计前提
- 要做并发、生命周期、资源释放这类「没有测试能证明对」的设计
- 团队里没人做过同类系统

判据（反写）：**凡是「我猜它应该是这样」的地方，都是必须去查的地方。** 不列正面清单——猜的地方无穷多，清单列不完。

仓内已有实现也是调研对象：动手前先确认这件事有没有人做过、最近的一份在哪。漏了这一步不是调研不足，是违反 **Reuse First**（`top-principles.md` §1）。

## 最低产出（三张表）

研究方法与三张表的字段见 `skills/research/technical-research-framework.md` 附录 G（数据源登记 / 证据清单 / 数字登记），不在此重复。

本流程只强制一条：**三张表在调研过程中边做边填，不事后补。** 事后补的表只能证明「我记得」，不能证明「当时查过」。

## 外部案例库

每次调研、每次线上故障，往 `templates/外部案例库.tpl` 追加一行。

字段：场景 / 别人的做法 / 结果 / 我们的结论（采纳 / 不采纳 / 改造）/ 出处。

用途：新项目开工先查这张表；「别人已经踩过的坑」不必自己再踩一遍。

## 红线

- 方案里出现「据说 / 一般是 / 应该支持」→ 回去补证据，或者删掉这句话
- 数字写不成一句完整口径 → 不用这个数字
- 只有结论、没有证据定位的调研，按未调研处理
