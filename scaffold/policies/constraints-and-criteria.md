# 约束与判据（规范该写什么、不该写什么）

> 目的：规范只压错误，不压能力。
> 由来：角色规范里混进"成员变量 ≤ 5 个""终态用 CAS"这类手段条款，执行者要么被束缚，要么阳奉阴违；而真正该硬的地方（契约、失败路径、性能阈值）反而没写。

## 0. 局部优化不代表全局优化

已升为最高准则 **Global Over Local**（`top-principles.md` §2），本文不重复其判据。它对本文所有规则都成立：一条规则只要能被遵守，就一定产生遵守成本，该不该留看的是**付出成本之后整体是否更好**，不是它让某个局部更好。凡是"为了让规则本身成立"而做的动作，先问它除了满足规则还改善了别的什么。

## 1. 一条规则的去留，由可判定性决定

**合格的规则：违反它时，别人能指着某个具体位置说「这里会出什么问题」。**

指不出具体位置、只能说"感觉不好""不够优雅"的，不是规范，是偏好。偏好不进规范。

三条处置：

| 情况 | 处置 |
|---|---|
| 能判定，且说的是"必须做成什么样" | 保留，写成判据（阈值 + 测量方法 + 失败样本） |
| 能判定，但说的是"必须怎么做" | 改写：把手段换成对结果的判据 |
| 判不出来 | 删掉，交评审者自由裁量；不要留在规范里当摆设 |

### 1.1 准入与退役（规则自身也是被约束的对象）

规则要**构成一组基**——少数几条，组合起来覆盖空间——不是一张越补越长的清单。所以规则本身按下面四条管：

- **准入**：新规则必须说出它挡住的一次具体失效（台账 / 复盘编号，或 file:line）。说不出的一律不进；同一失效面已有规则覆盖时，添第二条要先删掉第一条。
- **正交**：两条规则总是一起被违反、一起被满足 → 视为同一条，合并。一条规则若无法被单独违反，它不提供任何信息。
- **退役**：每批结束在复盘报告填「规则命中表」（`templates/retrospective.tpl`）——哪条命中、抓到什么、哪条零命中。**连续两批零命中的规则删除或降为样本**，不靠"以后可能有用"保留。
- **预算**：常驻上下文的文件（`templates/CLAUDE.md.tpl` 的开工链）有页数上限；超出的内容只能以指针形式加入，不搬正文。

## 2. 三层：约束 / 判据 / 手段

| 层 | 内容 | 写法 | 例子 |
|---|---|---|---|
| **约束** | 契约、边界、红线 | 违反即失败，不协商 | 只有 `infra/<vendor>/` 可 include 厂商头；公共头不出现厂商类型 |
| **判据** | 对结果的要求 | 阈值 + 测量方法 + 失败长什么样 | 并发用例跑 1000 次零失败；ASan/TSan 零报告；改一处行为只有对应用例红 |
| **手段** | 怎么实现 | **不写进规范** | 拆几个类、用什么容器、加不加锁、要不要引入某个模式 |

约束与判据的差别：约束是"不许做某事"，判据是"做到什么程度才算过"。两者都要可判定，都不规定路径。

### 2.1 数值条款的第三种用法：触发器

同一个数字有三种写法，效果完全不同：

| 写法 | 例子 | 问题 |
|---|---|---|
| 禁止线 | "函数不得超过 40 行，超了不合格" | 合理的复杂逻辑被强行切碎；执行者阳奉阴违 |
| 偏好 | "尽量短" | 判不出来，等于没写 |
| **触发器** | "超过 40 行时，写出为什么、能否拆、代价" | 既逼出隐藏决策，又不禁止合理例外 |

触发器的价值在于**把方案里没写出来的期望逼到台面上**：入参到第 6 个时，真问题通常不是"要不要打包成 struct"，而是"方案里是不是漏了一个概念"。

触发器写法必须同时给三样，缺一样就退化成禁止线：

1. **阈值**（从哪里来：技能默认 / 工具默认 / 项目自定，写清出处）
2. **超限后必须产出的书面判断**（为什么需要、能否合并拆分、代价）
3. **谁看这份判断**（评审者 / 架构师），以及没写算不算缺陷

判定对象因此从"数字"变成"有没有这段判断"。工具负责把触发自动化，人负责判断；工具缺失时按门禁口径记 FAIL，不得静默跳过。

### 2.2 判据的第三种失效：声明未接线

公开字段、指标或开关只要缺**写入点**或缺**消费点**，对它的判据就是恒真的：读到 0 永远成立，调用方配了等于没配。

| 声明 | 必须有的 | 判据 |
|---|---|---|
| 指标 / 计数器 | 写入点 + 读取点 | 两侧各有 `file:line`，`grep` 可判 |
| 配置项 / 开关 | 至少一个消费点 | 只校验范围而不被读取的不算接线 |
| 公开字段 | 至少一个写入点 | 恒为默认值的字段等于没实现 |

处置只有两条：接线，或删掉声明。审查时按 `skills/ai-code-review/SKILL.md` 纪律 5b 提 finding。

**同一份清单、多个消费方**：清单里出现的每个分组，必须至少有一个装载器认领它，其余装载器**跳过而不是报错**。把别人的分组报成「未知分组」，红灯会指向错误的子系统——本项目就出现过：`skills.conf.tpl` 早就带 `[agents]` 分组，而技能装载器只认两个分组，于是按模板建的新项目第一次跑布设自检，报的是「技能缺失 2」，实际角色已经装好了。判据是：拿模板生成一份清单，每个装载器的 `--check` 都退出 0。

### 2.3 判据的证据必须可达

终止态里写的 commit **不是「能 `git log` 出来」就算证据**：分支上开发、两次 rebase 之后，临时 hash 会变成孤儿对象，而台账照写 `closed`——同一个事实在两处记录，一处已经为假。

| 证据种类 | 判据 |
|---|---|
| 提交 | `git merge-base --is-ancestor <commit> <目标分支>` 退出 0 |
| run 目录 / 报告 | 路径在仓库内且被跟踪：`git ls-files --error-unmatch <path>` 退出 0 |
| 用例 | 证据 run 的 `stdout.log` 里出现过该用例名，且该 run 是证据级 |

复核时机：关账的同一次提交、复盘时抽查本批全部新 `closed` 行。写不进上面三类的证据，等于没写。

### 2.4 脚本把「正常」当失败：`pipefail` 下的零命中

`set -euo pipefail` 里 `$(grep … | sort)` 无匹配 = 非零退出 = 脚本**静默**终止，不打印任何诊断。凡是「零命中属正常」的采集（失败数、告警数、diff 行数）必须显式兜底 `|| true`，否则一次全绿的 run 会被记成失败，而失败现场恰恰不留线索。

复现：`bash -c 'set -euo pipefail; K="$(echo x | grep zz | sort)"; echo reached'` —— 不打印 `reached`。

判据是正反两向回放：零命中的历史输出必须通过，有命中的历史输出必须报出数。

同一个管道还有第二种吃法：右端用 `grep -q`。它**命中即退出**，左端（`ctest -N`、`find`、编译器输出）还没写完，就把下一行送进了已关闭的管道——141，`pipefail` 同样把它当失败。机器闲着时左端早写完就赢，有负载时输，同一条命令绿红随机；而 `stderr` 里只会留下你自己那句 FAIL，看不到 141。

处置：右端改成读尽的 `grep -c`（配 `|| true`），或者干脆去掉管道（`find … -print -quit`）。`grep -m1` 不解决问题——它只是把命中点提前。

### 2.5 夹具数报告值，不数通知次数

等待类夹具不能按**通知次数**计数：状态条件（`*_matched_status`、条件变量、`notify_one`）会把多次状态变化合并成一次唤醒，按次数计数就永远等不到 N——而且是随机的，同一份代码刷绿刷红。

证据形态是 A/B，两边都要留输出：改前 N 次里挂起若干次（且挂起 run 的计数停在 1 而不是 2），改后 N 次全过且耗时回到秒级。只给「改后全过」不算证据——它证明不了旧实现有问题。

## 3. 技能与规范的分工（防"引技能压上限"）

| | 技能（skills/） | 规范（policies/ + 角色规范） |
|---|---|---|
| 性质 | 方法内核，教怎么做 | 约束与判据，定做成什么样算过 |
| 允许主观 | 允许启发式、经验判断 | 不允许，必须可判定 |
| 强制力 | 参照执行，可按项目裁剪 | 违反即失败 |

推论：

- 技能里的硬性数值（文件行数、类规模、函数行数、入参个数）是**触发器**（§2.1），不是验收判据，也不是可忽略的偏好。项目可以不采纳某个阈值，但必须记一条偏离并写明替代判据；采纳则写进项目规范，交代阈值出处与超限处置。
- 技能不能被当成验收清单。验收只认判据。
- 角色规范只写职责、边界、红线、自检；**不写编码规范**——编码规范属于技能层，写进角色规范就会分叉成第二份。
- 条款之外给样本：`skills/cpp-exemplars/`（fmt / abseil / asio 的真实片段，含「看什么 / 不看什么」）。规则会腐化，样本不会；但样本只对照，不复制——许可证义务随代码走。

## 4. DoD 四块（任务卡固定结构）

任务卡只下发目标与边界，不下发手段。

1. **目标**：这张卡做完，能力上多了什么（调用方/用户可观察到的变化）
2. **边界**：不能碰的文件、接口、依赖方向、其他卡的范围
3. **验收判据**：可判定条件，按本卡风险选适用项——正确性 / 稳定性 / 性能 / 资源。不适用的写"不适用 + 理由"，不许留空
4. **证据**：落在哪（gate run 目录 / 用例名 / 报告路径）。缺证据等于没做

卡里不写实现步骤、不写文件行数、不指定数据结构。写了不但压上限，还会与实现现实脱节，最后必然违反或改卡。

## 5. 工程级与商业级的差别

不是"多做流程"，是判据的严格程度。归属哪一级由卡的用途决定，写进卡的目标块，不在规范里默认全都要。

| 维度 | 工程级（内部 / 研发阶段） | 商业级（对外交付） |
|---|---|---|
| 正确性 | 契约用例全过，错误路径有用例 | 外加变异检验：改一处行为，失败的用例恰好是对应那一组 |
| 稳定性 | 单次跑通 + 并发重复 N 次 | 长稳 T 小时、失败率上限、资源不随时间增长 |
| 性能 | 不劣化基线（相对上一版） | 有绝对 SLA 数字 + 压测报告 + 测量口径 |
| 故障 | 不崩溃 | 崩溃可诊断（日志/指标）+ 可恢复 |
| 兼容 | 内部接口 | 导出面 / ABI 冻结，破坏性变更走废弃流程 |

没有数字的"高性能"、没有时长的"稳定性"、没有失败样本的"可靠性"，一律不算判据。

## 6. 角色规范的骨架

角色规范（Dev / QA）只写四类内容：**职责、边界、红线、自检**。骨架见 `templates/role-dev.tpl`、`templates/role-qa.tpl`。

两边各有一条不能破的：

- **Dev 侧**：编码规范只引用技能，不复制正文；流程与提交格式只引用工程流程，不重述。数值条款按 §2.1 写成触发器：阈值 + 超限后必须产出的书面判断 + 谁看这份判断，三者缺一不可。
- **QA 侧**：维度清单只引用 `dimensions.md`；finding 字段与状态枚举只引用问题台账；终验结论只有"通过 / 不通过 / 未达清单"三档。非功能判据一律五元组，无阈值即"不可判"，不得签通过。

### 两种必然发生的漂移

1. **复制即分叉**：把上游条款抄进角色规范，上游改了而副本没改。实测已经发生过——提交类型列表与上游差一项、`fix` body 要求上游已废止的编号、把"九值状态"写成数字而枚举随后增加。
   → 处置：能引用的不复制；必须写的只写项目差异，并登记偏离记录。

2. **规范越界成手段**：为了"让执行更确定"，把实现方式写进规范（用 CAS、成员不超过 5 个、不得引入具名模式）。执行者要么被束缚，要么绕过，两者都会让规范失去公信力。
   → 处置：回到可判定性——这条能指出"违反后会出什么具体问题"吗？能，写成判据；不能，删或降建议级。

判断一个角色规范是否健康，一个问题够用：**把技能全部卸载，这份规范还能否独立判定"这次交付过不过"？** 答"不能"是对的——判定靠判据与证据，不靠技能朗读；答"能，因为规范里抄全了"才是病。
