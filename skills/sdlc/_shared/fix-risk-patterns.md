# 修改风险模式库（I 段专用）

> 作用：动别人（或上游）代码前，先对照已知风险模式。每条含「症状→根因→坑→应对」。
> 版本：v0.1 草案（2026-10-17）

## 分层修复原则（前置）

```
L1 自研层能 cover  →  不许下探
L2 下探原生/上游 API  →  每条必须写 8 要素 + 显式论证"为什么 L1 替代不了"
```

**8 要素**：背景 / 复现手段 / 精确改动点 `file:line` / 波及点 / 优点 / 缺点 / 隐患 / 验收。

## 模式 1 · 丢失唤醒（Lost Wakeup）

| 项 | 内容 |
|---|---|
| **症状** | 多线程并发首次等待时，部分线程误判超时失败，**而条件其实早已满足** |
| **根因三要素** | ① 状态标志是**对象级共享** ② 唤醒用 `notify_one()` ③ 被唤醒者**消费**掉共享标志 |
| **附加坑** | 超时路径不重算状态 ⇒ 空转到总超时结束 |
| **检测难点** | ⚠️ **TSan/ASan 抓不到**——标志是 atomic，无数据竞争，是**逻辑缺陷** |
| **应对** | `notify_all()` + 超时路径也重算状态 + 谓词用状态本身而非"变更标志" |

## 模式 2 · 硬编码超时穿透上层预算

| 项 | 内容 |
|---|---|
| **症状** | 用户设了 1s deadline，实际卡满 3s 才返回 |
| **根因** | 底层硬编码超时**在上层计时之外**发生，两者互不包含 |
| **坑** | 上层"有限默认 deadline"的承诺被静默突破，SLA 不可信 |
| **应对** | 超时可配 + 明确规则：**deadline 是全程预算，子超时从中扣除** |

## 模式 3 · 共享对象被覆盖配置

| 项 | 内容 |
|---|---|
| **症状** | 多个消费者各自设了参数，实际只有最后一个生效 |
| **根因** | 以为拿到的是独立实例，实际是**单一共享实例** |
| **坑** | 静默失效，不报错 |
| **应对** | 查 getter 是否返回同一指针；需要隔离就 per-consumer 实例 |

## 模式 4 · 过滤粒度错配

| 项 | 内容 |
|---|---|
| **症状** | 本该只收自己的消息，结果收到全量 |
| **根因** | 过滤键的粒度比预期粗（如用 Participant 前缀而非实例 ID） |
| **坑** | 随消费者数 N 线性放大 ⇒ **O(N) 接收放大**，每个消费者都承担全量 |
| **应对** | 明确过滤键粒度；需要 N 路隔离时，不要在同一通道里堆消费者 |

## 模式 5 · 文档与代码矛盾

| 项 | 内容 |
|---|---|
| **症状** | 注释/文档宣称 X，代码实际做 Y |
| **坑** | 后来者信注释 ⇒ 建立在错误前提上做设计 |
| **检测** | 对**注释里的断言**逐条做代码级核对，不能只读注释 |
| **应对** | 判定时以代码为准，文档标"待订正" |

## 通用隐患清单（动上游代码前必查）

- [ ] 改的是**安装头**（公开头）吗？⇒ ABI 破坏风险，需评审
- [ ] 有**同构代码**在别处吗？（如 Requester/Replier 对称实现）⇒ 同批修，否则留副本
- [ ] 该改动能被现有测试覆盖吗？不能 ⇒ 先写复现测试
- [ ] 有**行为依赖**该缺陷的代码吗？⇒ 修了可能引发连锁失败
