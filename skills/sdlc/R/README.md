## 1. 卡片清单

| # | 卡 | 输入 | 输出 | 状态 |
|---|---|---|---|---|
| R1 | 采集与结构化 | 用户一句话诉求 | 需求条目表（编号/陈述/来源/场景） | 待补 |

## 3. 与 S 段的关系

> 若目标域**存在标准规范**（如 OMG DDS-RPC），需求挖掘**不能替代**规范对齐：
> R 段产出的是"我们要什么"，S 段产出的是"规范要什么"，两者的**差集**才是架构的约束来源。

## 4. 退出条件 DoD

- [ ] 每条需求有编号、可判定的完成陈述、来源
- [ ] 每条需求已分级，且分级有证据支撑
- [ ] 需求与风险已联动（无"零风险需求"）
- [ ] 冻结基线已落盘，变更有记录

## 5. 反例

- ❌ 把"应该要…"当需求条目 ⇒ 不可判定
- ❌ 分级无证据 ⇒ 拍脑袋排期
- ❌ 未冻结就进入架构设计 ⇒ 需求漂移，架构返工
