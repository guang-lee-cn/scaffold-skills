# A2 · 架构方案

> 归属：`sdlc/A/`　版本：v0.1（2026-10-17）
> 上游：**A1 MVP 定界**　下游：**A3 架构复核**

## 1. 输入

| 参数 | 来源 |
|---|---|
| MVP 范围 + 裁剪清单 | A1 |
| 规范架构卡（若有） | S2 |

## 2. 目标

产出**可实施**的架构文档：组件、接口、数据流、状态机，且每一项可追溯。

## 3. 步骤

| # | 动作 | 判据 |
|---|---|---|
| 1 | 画组件边界 | 每个组件职责单一、可命名 |
| 2 | 定义组件间接口 | 每个跨组件调用有对应接口 |
| 3 | 画数据流（请求 / 回复 / 异常） | 三条路径齐全 |
| 4 | 定义状态机（生命周期 / 调用态） | 终态可达且唯一 |
| 5 | **建立追溯：组件 → 需求条目 或 规范条款** | 无孤儿组件 |
| 6 | 标注自研增强部分及其依据 | 见证据分级 |

### ⭐ 自研层的合理性判据（用户明确关注）

> 自研核心层（如本项目 Context）**不是"看起来分层了"就算合理**，必须能回答：
> 1. 它解决了原生 API 的**哪个**具体问题？（有 `file:line` 或行为证据）
> 2. 为什么这个问题**必须**在这一层解决，而不是在原生 API 层？
> 3. 它引入了什么新代价？（复杂度 / 性能 / 维护）
>
> 第 2 问答不出 ⇒ 该层是伪分层，应下推或删除。

## 4. 输出

`架构文档` —— 建议按 arc42 关键段组织：

| 段 | 内容 |
|---|---|
| 1 | 目标与约束（含合规口径） |
| 2 | 上下文 / 边界（依赖、外部系统） |
| 3 | 组件与接口 |
| 4 | 数据流与状态机 |
| 5 | 自研层正当性论证 |
| 6 | 风险与技术债 |
| 7 | 决策记录索引（→ ADR） |

## 5. 退出条件 DoD

- [ ] 组件 → 追溯 全覆盖，无孤儿
- [ ] 三条数据流（请求 / 回复 / 异常）齐全
- [ ] 状态机终态唯一可达
- [ ] 自研层三问已回答

## 6. 反例

- ❌ 组件无追溯 ⇒ 无法判断该不该存在
- ❌ 只画成功路径 ⇒ 异常路径是缺陷高发区
- ❌ 自研层只写"为了解耦" ⇒ 未论证，等于没论证
