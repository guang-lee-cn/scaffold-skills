> 上接：**A2/A4**　下接：**V 验证**

## 1. 卡片清单

| # | 卡 | 输入 | 输出 | 状态 |
|---|---|---|---|---|
| I1 | 基线锁定 | 当前代码状态 | 基线 tag/分支 + 备份 + 复验口令 | 待补 |
| **I2** | 修改方案（含**下探论证**） | 问题清单 | 8 要素方案书（逐条） | 待补 |
| I3 | 小步实施 | 已评审方案 | 一次一改的代码提交序列 | 待补 |

## 2. ⭐ 分层修复原则（硬性，体现"能不下探就不下探"）

```
L1  自研层（本项目 Context/Facade）能 cover  →  不许下探
L2  下探原生 / 上游 API                      →  必须写 8 要素 + 论证"为何 L1 替代不了"
```

**8 要素**（每条 L2 改动必须齐全）：

| # | 要素 | 说明 |
|---|---|---|
| 1 | 背景 | 问题发生的上下文与影响 |
| 2 | 复现手段 | 可复现步骤，或代码 review 路径（含 `file:line`） |
| 3 | 精确改动点 | `file:line`，不写"大约某处" |
| 4 | 波及点 | 谁依赖这里；有无同构代码（如 Requester/Replier 对称实现） |
| 5 | 优点 | |
| 6 | 缺点 | |
| 7 | 隐患 / 坑 | 见 `_shared/fix-risk-patterns.md` |
| 8 | 验收 | 具体命令与期望输出 |

> ⚠️ **L2 第 9 条隐含要求**：必须显式论证「为什么 L1 替代不了」。
> 写不出论证 ⇒ 不许下探。

## 4. 退出条件 DoD

- [ ] 基线已锁定，有 tag 或备份，可回滚
- [ ] 每条 L2 改动 8 要素齐全 + 下探论证已评审
- [ ] 每次提交只含一个逻辑改动，可单独 revert

## 5. 反例

- ❌ 未锁基线就改 ⇒ 无法回滚
- ❌ 把多个逻辑改动塞进一个提交 ⇒ 出问题时无法二分定位
- ❌ 改公开头文件不评审 ⇒ ABI 破坏
