# dispute-flow.md · 协作质疑-判定流（执行角色 → 决策方）

> 跨项目通用协作纪律：任何执行角色（Dev / QA / Test / 子 agent）**可以质疑上级决策**（架构师 / 主 agent 裁决），决策方必须判定合理性并给出处理方式。与工具、项目无关。
> 代码审查场景的质疑走 `ai-code-review` P5 回执（审查者↔实现者）；本流覆盖**协作层通用质疑**（方案可行性 / 资源 / 验收标准 / 工作分配 / 决策依据等非审查场景）。

## 1. 适用与触发

- **谁可以质疑**：任何被派发/被执行角色的协作者——不因"下行"而丧失质疑权
- **质疑对象**：上级决策（架构方案、验收标准、排期、资源分配、ADR 结论等）
- **触发条件**：发现决策基于错误假设 / 过时信息 / 未覆盖场景，且**能给出实证证据**（代码、测试输出、文档引用、数据）

## 2. 流程

```
提出质疑（finding 格式 + 实证证据）
 → 决策方判定：
    ├─ 成立   → 修订决策（记 ADR / 决策记录修订）+ 按协作台账派发处理
    ├─ 不成立 → 回复判定理由 + 关闭（质疑方无惩罚）
    └─ 存疑   → 双方收敛（≤2 轮）→ 未收敛 → G 终裁
```

### finding 格式（质疑必须可判定）
```
质疑: 一句话
对象: 决策/文档/编号
类别: 方案/资源/验收/排期/依据
证据: 代码原文或测试输出或文档引用（可追溯，禁止"我觉得"）
建议: 明确替代方案 + 影响面
定级: P0/P1/P2（P0=决策会导致正确性/契约/需求缺口）
```

## 3. 约束（防滥用，对齐 ai-code-review 纪律）

| # | 约束 | 原因 |
|---|---|---|
| 1 | **实证定级**：无证据的质疑不成立；先读代码/跑测试再质疑 | 防止为质疑而质疑（反过拟合） |
| 2 | **无惩罚**：质疑撤回或判定不成立不影响评价，编号保留 | 鼓励诚实暴露问题 |
| 3 | **≤2 轮收敛**：同题往返不超过 2 轮，未收敛 → G 终裁 | 防止对弈死循环 |
| 4 | **不重复质疑**：已判定的质疑除非有新证据，不重复提出 | 防止翻旧账消耗 |
| 5 | **判定必须回复理由**：不成立也要给技术理由（引用证据），不得情绪化/职权压制 | 保持质疑通道可信 |

## 4. 出口

- 成立 → 修订决策 + 按协作台账（如开发状态 J 区）登记派发
- 不成立 → 关闭记录（编号留痕，供复盘追溯）
- 存疑 → G 终裁（决策方与质疑方各自陈述证据，G 拍板）

## 5. 与既有纪律关系

- `ai-code-review`：审查流水线内质疑走 P5 回执 / 双向辩证 / 撤回无惩罚——本流是其协作层推广（非审查场景）
- `pj-core §2.2 接收反馈`：接收方（决策方）必须实证核验再判定，禁表演式同意——与本流互为镜像（一个约束提出方，一个约束判定方）
- 复盘：质疑-判定过程中暴露的决策缺陷按 `issues.md` 走 L1/L2 复盘
