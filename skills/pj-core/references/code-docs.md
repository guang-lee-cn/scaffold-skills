# code-docs.md · 代码注释与设计文档分层纪律

> 跨项目通用工程纪律：**设计意图/思路解释不进代码注释，写专门的设计意图文档**；代码只保留契约类标注。与语言、项目无关。
> 教训来源：MTComm 项目 J-02 拍板（大段设计意图注释→独立文档单一权威源），沉淀为公共纪律。

## 1. 两类注释的边界

| 类别 | 例子 | 落点 |
|---|---|---|
| **契约类标注**（消费方必须就近可见） | `@thread-safety` / `@lifecycle` / `@qos` / `@blocking` / `@scenario`、容量对齐、前置后置条件、返回值契约 | **留在代码**（接口头文件，随接口走） |
| **设计意图类**（为什么这么设计） | 演进考量、备选方案取舍、与上游差异理由、边界定义依据 | **迁出代码** → 独立设计意图文档（文件/Class/API 三级） |

## 2. 规则

1. **设计意图单一权威源**：解释性文档独立成文（如 `<module>-设计意图说明-<日期>.md`），代码中不再重复大段设计说明注释；
2. **契约标注保留**：接口头文件的五标注与容量/前置条件注释**不得删除**（跨 so 边界对消费方是硬契约）；
3. 代码中如需指引，只留一行短引用（如 `// 设计意图见 <文档路径>`），不展开；
4. 评审/交接时以设计意图文档为准核对实现，不以代码注释为凭。

## 3. 为什么

- 代码注释随代码腐化：实现改版后注释常残留过期理由，误导消费方；
- 大段注释无法被独立评审/追溯/交接；文档可评审、可版本化、可被第三方审核；
- 与提交纪律同源：**意图放文档，不塞代码注释，也不塞提交信息**（见 commit.md）。

## 4. 落地形态（参考 MTComm 实例）

- 文档：`<module>-设计意图说明-<日期>.md`（文件 → Class → 单个 API 三级意图 + §7 交接项）
- 台账：开发状态 J 区登记"注释精简 + 文档入库"交接项（验收=代码无大段设计说明注释、五标注完整）
- 第三方审核：设计意图文档作为审核稿提交（不依赖读代码猜意图）

## 5. 与既有纪律关系

- `commit.md`：提交信息只写 what/why 不写 how——意图同样不进提交信息
- `docs-templates.md`：设计意图文档按项目模板落位（如四角色写作接口 SOP 的架构产出）
