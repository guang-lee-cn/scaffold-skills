# workflow.md · 协作流程（门禁/心跳/批次/清单）

## 1. 执行模式（探 → 清单 → 确认 → 执行 → 验证 → 交付）

1. **动手前先探测**：核实环境、读全输入、定位事实，不靠猜测
2. **Action Plan 门禁**：实质操作前先输出动作清单 + 操作内容 + 附带信息（目标文件/路径、命令、影响范围、验证方式）→ G 确认 OK → agent 接管；G 明确授权的一次性小操作可直接执行
3. **执行最小化影响**：只动点名范围；不重写历史、不删用户文件
4. **验证**：用不同于生成路径的方式回读/抽查；远端操作后核实（git log / ls）
5. **交付**：产物注明权威路径与打开方式

## 2. 心跳约定（长任务可观测性，G 定案）

**目的**：长流程执行期间，G 可区分"卡死 vs 工作中"。

| 规则 | 内容 |
|---|---|
| R1 | 预计 >2min 的操作，**开头声明时长 + 阶段拆分**（"预计 N 分钟，阶段：A→B→C"） |
| R2 | **每阶段完成即反馈一行**（不等整体结束；格式：`✓ 阶段 i/N <内容>（耗时）`） |
| R3 | 后台等待/长轮询每 ~2 分钟报一次进度（不静默轮询） |
| R4 | **心跳中断 >3 分钟** = G 可判定异常并介入（不用猜） |
| R5 | **长等待任务（CI/远端构建/下载 >30min）不轮询**——完成后由 G 触发复查（G 偏好自主节奏） |

**长任务分级**：<2 分钟直接干 / 2-10 分钟声明+阶段心跳 / >10 分钟拆独立可观察段 / **>30 分钟外部等待（CI 等）声明预计时长后停止轮询，交 G 触发复查**。

## 3. 开发批次管线（串行→批次演进）

- 单单元串行（每次 1 API/脚本）→ 条件成熟转并行批次（每批 3-6 单元）
- 批次内单元高内聚（同子系统/同文件族）
- 每批交付**修改清单**（文件/单元/验证三列）供 G 检查，OK 后 **1 commit** 推送
- 批次间保留独立提交链，故障可单批回退

## 4. 修改清单标准模板（每小里程碑交付审核）

| 文件 | 单元 | 变更 | 影响面 | 验证结果 | 审批 |
|---|---|---|---|---|---|
| <路径> | <单元> | <内容> | <波及范围/风险> | <验证方式/结果> | 待批/已批 |

- 每小里程碑完成即交付（不等批次结束）；G 批准后方可提交

## 5. 效率纪律（编译/测试等待压缩）

1. **编译前快速验证**：改头文件/include 后，先 `g++ -fsyntax-only` 秒级检查，再全量编译（防多轮返工）
2. **测试失败自动判定**：全量失败 → 脚本自动单跑重试，区分偶发（环境竞态）vs 真失败（代码缺陷）；真失败禁止提交
3. **批量修改合并**：多文件改动一次脚本完成再编译（减少往返）
