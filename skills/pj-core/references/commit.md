# commit.md · Git 提交信息规范

## 格式

```
[<PROJECT>][<Type>] <做了什么>

1. <改动>
2. <改动>——<为什么，只有不显然的才写>

Fault: <公司编码>        # 仅当该缺陷已登记进公司级故障编码系统
验证：<用例名>           # 仅 Fix
```

## 类型集（冻结枚举，禁止自造词）

| Type | 用途 |
|---|---|
| `Add` | 新功能/新单元 |
| `Fix` | 缺陷修复 |
| `Refactor` | 结构调整 |
| `Test` | 测试新增/修正 |
| `Docs` | 文档 |
| `Chore` | 构建/CI/杂项 |

## 要点

- **标题只写做了什么，不写理由**。理由一律下正文。≤72 字符，动词开头，不加句号。
- **正文编号分条，一条一个改动**。只有"看 diff 猜不出来为什么"的改动才补理由；机械改动不写，别为凑格式硬编理由。空 body 不合格。
- **Fix 在正文后写一行验证用例**：回退这处修复，该用例应当变红。
- 正文只写 what / why，不写 how（命令、工具、环境细节进工作记录）。
- 禁黑话：内部术语/缩写首次出现用人话展开。自检标准是"陌生人 30 秒读懂"。
- **编号默认不带**。台账编号、卡片编号、决策编号只存在于内部文档；公共仓库的读者没有对应的解码表，写进去就是噪音。
  - 唯一例外：缺陷已登记进**公司级故障编码系统**时，写一行 `Fault: <公司编码>`。编码格式由公司系统定义，本规范不规定、不校验；未接入该系统前不写这行。
  - 内部要追溯缺陷，靠内部台账与开发状态，不靠 commit message。
- 禁止 AI 工具署名（`Co-Authored-By` 等）。
- **不重写历史**：未评审的本地 commit 可 amend；已进入评审或已合并的只增不改，修复用新 commit。

## 提交打包纪律

- **一个 commit = 一个可独立回滚的完整修改**。可回滚的判据：`git revert <sha>` 后仍能构建、相关用例仍通过。目标 ~100 行，单一逻辑变更 300 行内可接受，超过 1000 行必须拆。
- 不混装：格式化 / 重构 / 功能 / 测试修复分开提交；小范围重命名可随功能带。
- 代码与文档分开提交；日常文档更新不单独立提交，随关联代码或收口批次一起走。
- **push 以"一个完整工作单元"为单位**（一张卡 / 一个任务）：单元完成、评审通过、门禁过、工作树干净 → 一次 push。不逐 commit 推，也不攒跨单元大批；攒成大批说明单元拆错了。

## 示例

```
[<PROJECT>][Add] 实现 H 系列高层调用形态
1. H1 同步调用（call_sync 阻塞桥接）
2. H2 异步调用（按调用回调）——业务侧不能阻塞在调用线程上
```

```
[<PROJECT>][Fix] 修复回复配对键错位
1. related_sample_identity 在 requester 侧填错

验证：LateReplyAfterTimeoutIsDropped
```
