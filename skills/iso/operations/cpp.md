# 子系统实现纪律

> 上限：只写"什么算过"和"红线"。编码风格、类的拆法、容器的选型属于手段，由项目规范与执行者决定。
> 数值条款一律按 `scaffold/policies/约束与判据.md` §2.1 写成**触发器**：超线不判不合格，但必须写出「为什么需要 / 能否合并拆分 / 代价」，没写算 finding。

## 1. 上下文隔离（唯一的强约束）

进入子系统实现时，只允许引用三样东西：

1. 本页纪律
2. 本子系统的接口契约
3. 本子系统的设计文档

禁止引用全局需求描述与全局架构决策——那不是效率，是把无关信息当背景，让执行者按别人的假设写代码。

实现完成后写一句「本次引用的外部信息清单」，有空项说明原因。清单为空则不写。

## 2. 契约优先

先有接口签名与用例名，再写实现。契约歧义时**停下上报**，不得自行改契约：契约是多方共享的法律文件，单方面改动等于让别人在旧契约上继续工作。

## 3. 失败路径

错误码、返回值、异常三种表达方式在契约里只能出现一种。失败路径必须有对应用例；只测 happy path 等于没测。

返回码与观测的分工见 `skills/error-code-classification/`。

## 4. 注释

注释解释**为什么**，不解释**什么**。刻意的简化必须写明天花板与升级路径。

默认少写：一块注释最多 3 条可独立核实的断言，超了进设计文档、代码留一行带小节号的指针。写之前过三条判据（简明 / 稳定 / 可验证），再按四分类处置（契约保留 / 决策迁移 / 复述删除 / 协作元信息删除），见 `skills/comment-policy/`。

## 5. 测试

用例名表达行为语义，不表达实现结构；一个用例只钉一个行为。命名与结构判据见 `skills/test-naming-and-structure/`。

**变异检验**（商业级 / 关键路径才要求）：删掉修复点，对应用例必须红。用例在缺陷面前仍然绿，就是没钉住。

## 6. 何时回退

- 实现与架构假设冲突 → 暂停，输出偏差分析，由架构师重新评估
- 契约不可实现 → 暂停，给具体问题与修订建议，由架构师改契约后重新下发
- 发现更合适的成熟实现且满足原硬约束 → 暂停，走 `references/oss-adoption.md` 重新决策，不得自行引入依赖
