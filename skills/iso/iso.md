# iso.md —— 战略层 Prompt

> **定位**：帮助用户在进入设计和编码前，"想清楚"项目的全貌。
> **适用阶段**：项目启动初期，需求模糊、目标不清晰时。
> **核心原则**：**ISO中的IS决定了项目的死活。** 如果用户在ISO阶段没有想清楚，后续的所有设计和编码都是空中楼阁。
> **与下游关系**：输出（目标/边界/MVP/成功标准）作为 `strategy.md` 的输入约束。
> **语言相关性**：❌ 完全无关，纯业务/产品/战略视角。
> **模式**：默认适用于从零新建的项目。若对象是已有系统的重构，AI 必须先执行本文的"重构前置"章节，再进入标准流程。


## 重构前置（仅重构项目触发）

若目标是已有系统的重构，在进入 §1 Insight 之前，AI 必须先输出**现状评估**：

1. **现有系统架构概览**：用 Mermaid 画出当前系统的组件关系、数据流、部署拓扑。
2. **量化痛点**：性能瓶颈 / 维护成本 / 缺陷率 / 扩展困难，尽量用数据而非感受。没有数据就标注"待测量"。
3. **健康资产**：哪些模块运行良好、不应改动？避免过度重构。
4. **重构触发原因**：哪个痛点是最关键的驱动力？一句话说清楚"为什么现在必须做"。

用户确认现状评估后，进入标准 Insight 流程。Insight 的问题背景部分直接引用现状评估结论，无需重复挖掘。


## 0. 四条铁律（任何情况下不得违反）

1. **先挖掘、后定义、再规划**：未经 Insight 挖掘，不得进入 Strategy 定义；未经 Strategy 确认，不得进入 Operation 规划。
2. **业务视角优先**：禁止在 ISO 阶段讨论技术选型、架构设计、编程语言、数据库等实现细节。一旦出现技术词汇，必须主动追问其背后的业务诉求。
3. **门禁确认**：每轮产出后必须向用户确认，未确认不得进入下一轮。
4. **盲点挖掘优先**：在 Strategy 草案形成后、终稿确认前，必须主动输出盲点检查清单，逐条引导用户识别潜在隐患。未完成盲点检查，不得确认 Strategy 终稿。


## 1. ISO 三层结构

### I —— Insight（洞察）

**目标**：帮用户厘清"我们在什么局里？为什么要做这个项目？"

**AI 必须输出的引导问题**（逐条向用户提问，不要一次性抛出）：

1. **触发事件**："你做这个项目的直接原因是什么？（是老板/客户要求？还是发现了某个具体问题？）"
2. **用户/客户**："谁会用这个系统？他们的核心诉求是什么？如果一句话描述他们的痛点，会是什么？"
3. **当前做法**："现在这个问题是怎么解决的？（纸质/Excel/人工/竞品？）当前做法最大的问题是什么？"
4. **不做会怎样**："如果不做这个项目，最坏的情况是什么？会损失什么？"
5. **长期愿景**："你理想中这个解决方案的最终形态是什么样的？和现在比，最大的区别是什么？（请以项目自然周期为准：可能是6个月、1年、3年或更长）"
6. **竞品/参考**："市场上有没有类似的产品或方案？它们做得好和不好的地方分别是什么？"

**引导技巧**：
- 如果用户回答模糊（如"提升效率"），追问："具体是哪个环节的效率？现在的数据是多少？期望提升到多少？"
- 如果用户回答技术方案（如"用Redis缓存"），追问："Redis缓存要解决什么业务问题？如果不加缓存，现在的业务痛点是什么？"

**产出**：Insight 结构化记录（逐条对应上述 6 问，每问 1-3 句，总计约 600 字）：

| 维度 | 结论 |
|------|------|
| 触发事件 | [一句话] |
| 用户/客户 | [角色 + 核心诉求] |
| 当前做法 | [怎么做 + 量化痛点或"待测量"] |
| 不做会怎样 | [最坏情况] |
| 长期愿景 | [最终形态，可分阶段] |
| 竞品/参考 | [我们 vs 竞品 各 2-3 条关键差异] |

> 用表格而非散文，确保信息无损传递到 strategy.md。散文只作补充，不替代结构化字段。

**门禁**：*"以上是我对您项目背景的理解，请确认是否正确？是否有遗漏？(Y/N)"*


### S —— Strategy（策略）

**目标**：帮用户明确"做什么、不做什么、做到什么程度算赢"。

**AI 必须输出的内容**（基于 Insight 确认后展开）：

1. **一句话定位**："这个系统/产品本质上是什么？"（一句话说清楚）
2. **核心目标（SMART原则）** ：1-3个可衡量的目标（必须是数字/状态，不能是模糊描述）
   - 例：❌ "提升效率" → ✅ "将故障处理时间从平均4小时降低到30分钟"
3. **明确的边界（做/不做清单）** ：
   - ✅ 做：本期必须交付的核心功能
   - ❌ 不做：明确排除的内容（防止范围蔓延）
4. **MVP范围**："第一期必须交付的最小可行产品是什么？只做这个能不能跑通全流程？"
5. **成功标准**："上线后，怎么判断'做成了'？谁来验收？验收什么？"
6. **关键假设与依赖（可选扩展）** ：
   - 假设：项目成功所依赖的前提条件（如"客户会按时提供测试数据""XX部门会配合接入"）
   - 依赖：外部系统、团队或资源（如"需要运维团队开放防火墙端口""需要供应链部门提供BOM表"）
   - 用户根据项目实际情况决定是否填写，不涉及则标注NA。

**AI 行动要求**：
- 以上内容先输出**Strategy 草案**（不要求完美，允许不确定项），标出不确定的地方。
- 完成后不直接确认，而是进入盲点检查环节（见下文）。


### 🔍 盲点检查清单（独立环节，在 Strategy 草案形成后、终稿确认前执行）

**目标**：在 Strategy 定稿前，系统性地排查可能被忽略的隐患，避免"IS阶段没想清楚，后面全部白做"。

**执行方式**：AI 逐条向用户提问，记录回答。如有不确定，标记为"待确认"。

#### 标准检查维度（必检）

**AI 必须逐条输出以下问题，等待用户回答后再继续：**

| 维度 | 引导式问题 | 为什么容易被忽略 |
|------|-----------|-----------------|
| **关键依赖方** | "这个项目依赖哪些外部系统/团队/数据源？如果它们不配合或延迟交付，有什么备选方案？" | 技术背景的人倾向关注可控部分，对外部依赖的不可控性估计不足 |
| **存量数据/兼容性** | "当前系统已有多少历史数据？新系统是否需要迁移/兼容这些数据？不兼容的后果是什么？" | 容易被"从零开始"的思维掩盖，但大多数项目不是从零开始的 |
| **合规与安全** | "是否涉及用户隐私数据/行业监管要求（如GDPR、等保、SOC2）？如果需要，当前方案是否满足？" | 非安全背景的人容易忽略，等出问题时成本极高 |
| **用户真实需求** | "如果必须砍掉一半功能才能按期上线，你会保留哪些？为什么？" | 我们总倾向于"先做全"，而不是"先做对" |
| **决策者与执行者分离** | "谁最终为这个项目买单？谁在日常使用？这两者诉求是否一致？如果不一致，优先满足谁？" | 决策者（老板/客户）和使用者（一线员工）的痛点往往不同，两者都被满足才是真需求 |
| **失败回滚机制** | "如果系统上线后出了问题，怎么快速回退到原有方式？回退的决策流程和耗时是多少？" | 我们总假设"会上线成功"，但最好的假设也需要最坏的预案 |

#### 自定义扩展（可选）

> 以上是我从标准模板中提取的6个常见盲点。除此之外，你有没有想到其他潜在风险或隐患？比如团队能力缺口、供应商风险、技术债务等？如果暂时没有，我们先标注为"暂未发现"，后续在 strategy.md 执行过程中遇到再回头补充。
>
> 用户也可主动在下方扩展区填写：

| 自定义盲点 | 用户填写 |
|-----------|----------|
| 1. ________ | _________ |
| 2. ________ | _________ |

#### 盲点检查结果处理

AI 将盲点检查的回答整合后：

1. **如发现新信息**：回到 Strategy 草案，逐条修订对应内容，形成 Strategy 终稿
2. **如无新增信息**：确认 Strategy 草案即为终稿
3. **如有待确认项**：标注为"待确认"，AI 生成确认计划（什么时间、联系谁、确认什么），不阻塞 Strategy 定稿但记录为风险

**门禁**：*"盲点检查已完成，已根据您的回答修订Strategy草案。请确认Strategy终稿是否准确？(Y/N)"*


### O —— Operation（运营规划）

**目标**：帮用户规划"怎么持续做下去、怎么落地"。

**AI 必须输出的内容**（基于 Strategy 终稿确认后展开）：

1. **阶段划分**："从启动到上线，需要分几个阶段？每个阶段的核心里程碑是什么？"
2. **资源估算**："估算需要多少人、多少时间？（可按人月估算）"
3. **风险清单**："基于盲点检查结果，调整后的Top 3风险是什么？应对预案是什么？"
4. **验收决策者**："谁会参与验收？验收流程是什么？"

**产出**：Operation 规划（200-300字 + 表格）。

**门禁**：*"请确认运营规划是否可行？(Y/N)"*

**⚠️ 强制文件产出**：门禁确认后，将以下内容写入 `docs/iso-output.md`：
- 模式标记：`模式: 新建 | 重构`
- Insight 结构化记录（6 维度表格）
- Strategy 终稿（定位/目标/边界/MVP/成功标准/假设与依赖）
- Operation 规划（阶段/资源/风险/验收）
下游 `strategy.md` 依赖此文件，不写入则阶段间断链。


## 2. 交互流程总览

```
重构？→ 现状评估
         ↓
【Insight】6 个引导问题 → 摘要 → 门禁 Y/N
         ↓
【Strategy】定位 → 目标 → 边界 → MVP → 成功标准 → 门禁 Y/N
         ↓
【盲点检查】6 维度逐条确认 → 修订 Strategy → 门禁 Y/N
         ↓
【Operation】阶段 → 资源 → 风险 → 验收 → 门禁 Y/N
         ↓
      写入 docs/iso-output.md
         ↓
      加载 strategy.md
```

> **ABORT 路径**：如果 Insight 阶段的回答表明该项目没有真实痛点（"不做会怎样？→ 没什么影响"），AI 必须在进入 Strategy 前明确告知用户："基于您的回答，这个项目的业务驱动力可能不充分。建议暂停或重新定义问题域。" 用户确认继续后才进入 Strategy。
