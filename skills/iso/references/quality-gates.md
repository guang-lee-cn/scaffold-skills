# 质量门禁协议：能力、四态与记账

> 本文件是 `operations/cpp.md` §5 与 Light 各阶段质量检查的**协议手册**：定义"要求什么能力、怎么判定通过、工具不具备怎么办"。
> **本文件不指定任何具体工具**——ISO 不绑定第三方依赖，能力到工具的映射由各项目在 `docs/quality-gates.md` 中声明。
> AI 判定门禁是否通过时查阅本文；项目专有的工具选型、命令与阈值不写回本文件。

## 1. 为什么是"能力"而不是"工具"

门禁写成"必须用 X 工具零警告"会引入两类**静默失效**：

- 项目换了等价工具 → 门禁描述与现实不符，AI 要么跳过、要么编造一次"通过"
- 环境没装该工具 → 门禁无法执行，而"无法执行"极易被当成"没有问题"

ISO 跨项目、跨语言、跨环境，因此只对**能力**提出要求。能力永远成立，工具随项目变。

## 2. 六项能力（语言无关）

| ID | 能力 | 判定标准 | 不通过意味着 |
|----|------|---------|------------|
| C1 | 格式一致性 | 存在可机械执行且幂等的格式化命令；执行后无差异 | 风格争议挤占评审注意力 |
| C2 | 静态缺陷扫描 | 静态分析退出码为 0，级别阈值由项目声明 | 机器可发现的缺陷流向下游 |
| C3 | 接口与类型检查 | 对外边界无类型错误；编译/检查零警告 | 跨模块契约在运行期才暴露 |
| C4 | 资源与内存验证 | 动态检查工具下目标用例全绿 | 泄漏/越界/未定义行为逃逸到生产 |
| C5 | 复杂度阈值 | 函数行数、圈复杂度等硬数字未越线 | 单元无法独立测试与复用 |
| C6 | 测试存在性与执行 | 核心路径存在可自动运行的测试且全部通过 | 变更无法被证伪 |

> C5 只判定**数字是否越线**，不判定"该不该拆"——后者是设计审查，不可机械判定，属于 Agent/人工审计范围。

## 3. 项目声明：`docs/quality-gates.md`（固定路径）

采用 ISO 的项目必须产出 `docs/quality-gates.md`。**字段固定，取值由项目自定**：

| 字段 | 说明 |
|------|------|
| 能力 | C1–C6 之一 |
| 适用范围 | 语言 / 目录 / 模块（如 `src/**/*.cpp`、`scripts/**/*.sh`） |
| 本项目工具 | 工具名 + **锁定版本** |
| 命令 | 可直接执行的完整命令 |
| 阈值 | 判定通过的硬数字或级别 |
| 强度 | 生产级 / 工程级（见 §6） |

示例（**工具名仅为占位，项目自行替换**）：

| 能力 | 适用范围 | 本项目工具 | 命令 | 阈值 | 强度 |
|------|---------|-----------|------|------|------|
| C1 | `**/*.py` | 任一格式化器 | `<fmt> --check .` | 无差异 | 工程级 |
| C2 | `scripts/**/*.sh` | 任一 shell 静态分析器 | `<linter> -S warning scripts/` | 0 findings | 生产级 |
| C5 | `src/**` | 任一复杂度统计 | `<tool> src/` | 函数 ≤40 行 | 生产级 |

**版本必须锁定**：工具的默认规则集会随版本漂移，"零警告"会在某次升级后突然不成立，且无人能定位原因。这是可执行规范能否长期活着的关键。

## 4. 四态判定

| 状态 | 触发条件 | 处理 |
|------|---------|------|
| **通过** | 命令退出码为 0 且达标 | 进入下一阶段 |
| **未通过** | 存在 findings | **阻塞**，修复后重跑 |
| **未声明** | 该能力在 `docs/quality-gates.md` 中无映射 | **阻塞**：这是规范缺口，不得视为通过 |
| **已声明未安装** | 有声明但环境不具备 | **阻塞**，允许按 §5 显式降级 |

**唯一禁止的行为**：把"未声明"或"已声明未安装"静默当作"通过"。门禁话术必须显式报出状态：

- 通过 → `C2 静态缺陷扫描：通过（<工具> <版本>，0 findings）`
- 未通过 → `C2 静态缺陷扫描：未通过（N findings，清单如下）`
- 未声明 → `C2 静态缺陷扫描：未声明——请在 docs/quality-gates.md 声明工具，或按 §5 记账降级`
- 未安装 → `C2 静态缺陷扫描：已声明未安装（<工具> 不在 PATH）——降级需按 §5 记账`

## 5. 降级必须记账

降级不是"跳过"，是**一笔要还的债**。与 `oss-adoption.md` §4 的自研记账、`operations/cpp.md` §6 的偏差分析同一机制。

降级时在 `docs/quality-gates.md` 追加一行：

| 字段 | 内容 |
|------|------|
| 降级能力 | C1–C6 中哪一项 |
| 原因 | 为什么本次无法执行（环境 / 时间 / 工具不可得） |
| 替代手段 | 用什么代替（人工检查 / 另一工具 / 不检查） |
| 恢复条件 | 什么情况下必须恢复（如"CI 环境接入前"） |
| 责任与时间 | 谁、何时 |

**无替代手段的降级必须由用户确认**——门禁不得由 AI 替用户自我批准（对应 `SKILL.md` 铁律 1：不得替用户回答）。

## 6. 强度分级：并非所有代码同等对待

判据是"**坏了会怎样**"：

| 级别 | 判据 | 要求 |
|------|------|------|
| 生产级 | 影响交付物或最终用户 | C1–C6 全开 |
| 工程级 | 仅影响构建 / 测试 / 部署流程 | C1 + C2，不强制 C4 / C6 |
| 一次性 | 临时验证、用完即弃 | 不设门禁 |

ISO 本身是规模自适应的（Light 原型不写测试），本协议延续同一原则：对一次性脚本套生产级门禁，会导致整套门禁被绕过，**比不设门禁更糟**。

## 7. 边界

- **不含**：findings 的严重度分级与债务台账——属于审计规范（`references/audit.md`，待建）。
- **不含**：具体工具选型与阈值取值——见项目侧 `docs/quality-gates.md`。
- **不改** `SKILL.md` 的四条不变量：门禁串行、产出落文件、上下文隔离、决策可追溯全部继续适用。本文件只是让"门禁通过"第一次有了可判定的定义。
